## 4. Blocking defects — must be fixed before any submission

### 4.1 The objective function is a constant. The model optimises nothing. **[FATAL]**

The objective is

$$\min \; Z = \sum_{i=1}^{5}\sum_{j=1}^{15} t_j\,x_{ij}$$

and Constraint 1 (Coverage) requires $\sum_{i} x_{ij} = 1$ for every $j$. Substituting:

$$\sum_{i}\sum_{j} t_j x_{ij} \;=\; \sum_{j} t_j \left(\sum_{i} x_{ij}\right) \;=\; \sum_{j} t_j \cdot 1 \;=\; \sum_{j} t_j \;=\; 8.985$$

$t_j$ depends only on the fault, never on which group serves it. **Every feasible assignment has objective value exactly 8.985 h.** The solver is not choosing a good assignment; it is returning the first feasible point it finds.

Three independent confirmations, all already inside the repository:

- **The solver log** (cell 25 output): `Continuous objective value is 8.985` at the LP relaxation, then `Integer solution of 8.985 found by feasibility pump after 0 iterations and 0 nodes`, then `Search completed - best objective 8.985, took 0 iterations and 0 nodes`. CBC did **zero** branch-and-bound work — the standard signature of a constant objective.
- **The baseline notebook** (`04`, cell 9 output): the *random* assignment reports `Total travel time: 8.985 hours` — bit-for-bit identical to the "optimal" solution. The repository proves its own null result.
- **The cell comment** in `02`, cell 15 reads `# initial obj function` — suggesting the team knew this objective was provisional and the multi-objective version was never substituted in.

**Consequence for the paper:** any sentence of the form "the optimisation model reduced travel time" is false as written. A reviewer running the notebook finds this in under ten minutes, and it reads as either a serious error or worse. **This must be fixed, not worked around.**

**Why no patch of the current objective will work:** *any* objective whose cost depends only on the fault index $j$ is invariant under a "serve every fault exactly once" constraint. Multiplying by 2 for a return trip does not help. There are exactly three escapes:

| Escape route | Requirement | Feasible by Friday? |
|---|---|---|
| **(a)** Make cost group-dependent, $t_{ij}$ | Crews must start from different depots/stations. Requires new data from ECG. | ❌ No — blocked on external data |
| **(b)** Full vehicle routing with inter-town travel | Requires a 23×23 town-to-town distance matrix. Not collected. | ⚠️ Only via an API-derived matrix; risky in 3 days |
| **(c)** **Optimise response time, not travel time** | Uses **only the data already in hand**. | ✅ **Yes — recommended** |

**Recommended fix (c), in one sentence:** the quantity a customer actually experiences is not the crew's travel time to them, it is **how long they wait from shift start until a crew arrives** — and that *does* depend on the assignment and on the order in which a crew works its jobs. Introducing position-indexed variables makes the problem genuinely combinatorial, makes the equity constraint meaningful, and makes `Priority` usable at last. Formulation in §6.

### 4.2 The equity constraint contains no decision variables. It is inert. **[FATAL]**

In `02`, cell 23, the team correctly builds `near_avg_travel` and `far_avg_travel` as PuLP expressions — and then discards them. The constraint actually added to the model is:

```python
prob += (pulp.lpSum([travel_time[j] for j in far_faults]) / len(far_faults)
         <= theta * pulp.lpSum([travel_time[j] for j in near_faults]) / len(near_faults),
         "Equity_Constraint")
```

Both sides are sums over **plain Python floats**. No `x` variable appears. The constraint evaluates to the fixed comparison `0.7477 ≤ θ × 0.4689`, which is a property of the *input data*, not of the solution. It constrains nothing.

Worse, it is a **latent infeasibility trap**. Verified over θ:

| θ | Constraint evaluates to | Model behaviour |
|---|---|---|
| 1.50 | `0.7477 ≤ 0.7033` → **false** | Reports **INFEASIBLE** for every assignment |
| 1.55 | `0.7477 ≤ 0.7268` → **false** | Reports **INFEASIBLE** for every assignment |
| **1.60** | `0.7477 ≤ 0.7502` → true | Vacuously satisfied. **Slack = 0.15 minutes.** |
| 1.70 | `0.7477 ≤ 0.7971` → true | Vacuously satisfied |

The observed Far/Near ratio is **1.5947**, and θ was set to **1.6**. The model works only because θ was tuned to sit 0.15 minutes above the data. Note that `03_diagnostics.ipynb` uses `theta = 1.5` — which would render the model infeasible — and this almost certainly explains why a diagnostics notebook was needed at all. **A reviewer who changes θ by one decimal place gets "INFEASIBLE" and will draw the obvious conclusion.**

The README carries the same error at the level of theory. Its "fully linearised" equity form,

$$\sum_{j:z_j=\text{Far}} t_j \;\le\; 1.6\cdot\frac{N_{\text{Far}}}{N_{\text{Near}}}\cdot\sum_{j:z_j=\text{Near}} t_j$$

is **algebraically correct** (verified: $5.2340 \le 5.2514$, identical to the ratio form) — but both sides are sums of the *input parameters* $t_j$, with no $x_{ij}$ anywhere. So the defect is not a slip in the code; it is in the formulation itself. The team derived a constraint on the data rather than on the decision. The root cause is the same as §4.1: treating $t_j$ as the quantity a customer experiences, when $t_j$ is fixed by geography and entirely independent of any dispatch decision. **The equity concept has to be re-anchored to something the model can move** — response time, not travel time (§6).

### 4.3 The multi-objective model described in the README was never implemented. **[MAJOR]**

The README specifies

$$\min Z = \alpha\left(\sum_i\sum_j t_j x_{ij}\right) + \beta\,(R_{\text{Far}} - R_{\text{Near}})$$

`02` cell 8 defines `alpha = 0.7`, `beta = 0.3`, prints them — and cell 15 then sets a single-objective, travel-time-only objective. **α and β never enter the model.** The paper's central methodological claim (a weighted efficiency–equity trade-off) is undelivered. There is also no Pareto/weight-sensitivity analysis, which is the standard expectation for any multi-objective paper.

### 4.4 The baseline is not a benchmark, and it is infeasible. **[MAJOR]**

`04_baseline_model.ipynb` draws **one** random assignment at `seed=61` and compares against it. Three separate problems:

- **n = 1.** A single draw has no sampling distribution, no confidence interval, no statistical content. Any claimed improvement is anecdote.
- **It is infeasible.** The notebook's own final cell reports `Group 1: 11.667h work time (exceeds 8h shift)`. Comparing a feasible optimum against an *infeasible* alternative is not a valid comparison — the optimum wins by construction, on constraint satisfaction rather than on objective value.
- **It is the wrong counterfactual.** Round-robin over a shuffle is a straw man. The comparison a reviewer wants is against **current ECG practice** (how does the Hohoe depot actually dispatch today?) and against a **sensible heuristic** (greedy nearest-first, or zone-clustered assignment).

Because of §4.1, the reported travel-time comparison is 8.985 vs 8.985 — a **0.0% improvement**. There is presently no measured benefit from optimisation anywhere in this repository.

### 4.5 Travel is modelled as if crews teleport home for free. **[MAJOR — formulation realism]**

$t_j$ is depot→fault travel, counted **once** per fault. A crew assigned three faults is charged one one-way trip to each, with no return leg and no inter-fault travel. Physically, a crew either (i) returns to the Hohoe depot between jobs — in which case the cost is $2t_j$ — or (ii) travels fault-to-fault, which requires an inter-town matrix the project does not have. Either way the current accounting understates real travel by roughly a factor of two and removes all routing structure. The paper must state the dispatch protocol it assumes and justify it operationally (ECG crews plausibly *do* return to base for materials — **confirm this with Abdul Haliq**; it converts a modelling weakness into a documented field assumption).

### 4.6 The faults dataset is simulated but framed as a case study. **[MAJOR — research integrity]**

The title says *"A Case Study of Hohoe Operations Department."* The towns and travel times are real. **The 15 faults are not** — they are `random.choices()` draws with an invented fault-type distribution (`[0.15, 0.25, 0.20, 0.15, 0.10, 0.15]`) and an invented priority split (30/70). No source is given for either distribution.

This is **not** a fatal problem — simulated demand against a real network is a completely standard and acceptable design. It becomes fatal only if it is not disclosed. Required:

- The abstract and Methods must say **explicitly** that fault instances are synthetic.
- The fault-type and priority distributions need a source: ECG Hohoe's historical fault log (best), an interview-elicited estimate (acceptable, cite the interview), or an explicit "assumed for illustration" label (weakest, but honest).
- Consider retitling to something that does not overclaim, e.g. *"…: A Simulation Case Study Grounded in the Hohoe Operations Department."*

## 5. Secondary defects

### 5.1 Experimental design is a single instance
One day, 15 faults, one random seed, one solver, one parameter setting. There is no scaling study, no replication, no sensitivity analysis, and no solve-time reporting. For an optimisation paper this is the most common desk-reject trigger after formulation errors.

### 5.2 The zone rule is unstable and contradicts the README
`01` cell 6 sets the Near/Far threshold to `ceil(max(distance))/2` = `ceil(38.4)/2` = **19.5 km**. The README states **"Near: ≤ 20 km, Far: > 20 km."** These disagree, and they disagree on a town that is in the data: **Liati at exactly 20.0 km** is classified `Far` by the code and would be `Near` by the README rule.

More seriously, the threshold is a **function of the maximum observed distance**. Add one town 50 km out and the threshold jumps to 25 km, silently reclassifying Golokwati, Wli, and Leklebi. A zone definition must be an exogenous, operationally justified constant — ideally ECG's own service-area convention. **Ask ECG what threshold they use**; if none, fix 20 km and justify it.

So Constraint 2 is rigid, Constraint 3 is slack, and Constraint 4 is inert (§4.2) — **Constraint 1 and Constraint 2 between them leave almost nothing to decide.** This must be addressed by varying the instance size (§8, Day 2) so that the constraints actually interact.

In a real utility, priority is the *primary* dispatch driver (a downed line near a clinic outranks routine maintenance). Either use it — as an objective weight, or as a constraint forcing High-priority faults into early positions — or remove it from the dataset. Leaving it unused invites the question "why is this column here?"

## 6. Recommended reformulation

The fix that rescues the project using **only data already in hand**: stop optimising total travel (a constant) and optimise **customer response time**, which depends on both the assignment *and* the service order.

**New sets and variables**

- $K = \{1,2,3\}$ — service positions within a crew's shift.
- $y_{ijk} \in \{0,1\}$ — crew $i$ services fault $j$ in position $k$. (5 × 15 × 3 = 225 binaries — trivial for CBC.)
- $R_j \ge 0$ — response time: hours from shift start until a crew reaches fault $j$.
- $C_{\max} \ge 0$ — makespan.
- $G \ge 0$ — equity gap.

**Job occupancy** (assuming crews return to the Hohoe depot between jobs — *confirm with ECG*): $s_j = 2t_j + r_j$.

**Constraints**

| # | Constraint | Meaning |
|---|---|---|
| C1 | $\sum_i \sum_k y_{ijk} = 1 \;\; \forall j$ | Coverage |
| C2 | $\sum_j y_{ijk} \le 1 \;\; \forall i,k$ | One job per slot (replaces the old capacity constraint) |
| C3 | $\sum_j y_{ijk} \ge \sum_j y_{ij,k+1} \;\; \forall i,k$ | No idle gaps in a crew's schedule |
| C4 | $\sum_j\sum_k s_j y_{ijk} \le H \;\; \forall i$ | Shift feasibility |
| C5 | $R_j \ge \sum_{k'<k}\sum_{j'} s_{j'} y_{ij'k'} + t_j - M(1-y_{ijk})$ | Response time (big-M, tight under minimisation) |
| C6 | $C_{\max} \ge \sum_j\sum_k s_j y_{ijk} \;\; \forall i$ | Makespan |
| **C7** | $\bar R_{\text{Far}} \le \theta\,\bar R_{\text{Near}}$ | **Equity — now genuinely a function of $y$** |

**Objective**

$$\min \; \alpha \cdot \underbrace{\frac{1}{|J|}\sum_j R_j}_{\text{efficiency}} \;+\; \beta \cdot \underbrace{G}_{\text{equity, } G \ge \bar R_{\text{Far}} - \bar R_{\text{Near}}}, \qquad \alpha+\beta=1$$

**Why this works**

- The objective is **not** constant — $R_j$ depends on which crew takes fault $j$ and in what order, so the solver has a real combinatorial problem.
- The equity constraint **contains decision variables**, so θ finally does something and a θ-sweep becomes a publishable sensitivity result.
- α and β **actually appear**, making the multi-objective claim real and enabling a **Pareto frontier** figure.
- `Priority` becomes usable — weight $R_j$ by priority, or add $\sum_k k\,y_{ijk} \le 2$ for High-priority faults.
- It is a recognised model class (**parallel-machine scheduling with position-indexed assignment**), which gives you a literature to cite and a defensible methods section.

> A feasibility probe of exactly this formulation was run against the project's own data during this audit to confirm it solves and is non-degenerate. See §9 for the result.

## 7. What a referee will say

### 7.1 The three questions that decide the outcome

### 7.2 Literature engagement is currently zero
The `# References` section is empty and no related work is cited anywhere. You need **20–30 references minimum**, across four clusters:
- **Generalised assignment / parallel-machine scheduling** — the formal home of your model.
- **Technician routing & scheduling (TRSP)** and field-service workforce scheduling — your direct methodological neighbours.
- **Equity/fairness in facility location and service allocation** — where θ and the min-gap objective come from; this is where your novelty claim lives.
- **Power-distribution outage management and crew dispatch**, ideally including sub-Saharan African utility studies — your application context.

This is a real half-day of work and is the single most common reason applied-OR case studies get desk-rejected.

### 7.3 Novelty positioning
The model itself is a standard assignment/scheduling MILP — do not claim methodological novelty there; you will lose. Claim contribution on: **(i)** the equity-constrained formulation applied to rural electricity restoration, **(ii)** the primary field data from an operating Ghanaian utility, **(iii)** the quantified efficiency–equity trade-off curve as a decision aid for distribution utilities. Frame it as an **application/case-study paper**, which is what it is and what it can defend.
